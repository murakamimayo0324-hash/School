# /goal 完了条件の書き方ガイド（詳細）

`goal-prompt-builder` スキルの補助資料。条件文の整形で判断に迷ったとき、良い例/悪い例を
確認したいとき、`/goal` の運用仕様を確認したいときに読む。出典は Claude Code 公式ドキュメント
（<https://code.claude.com/docs/en/goal>）。

## 1. `/goal` の仕組み

- `/goal <完了条件>` を打つと、その条件を directive として即座に1ターンが始まる。別途プロンプトを送る必要はない。
- **毎ターン終了後**に、小型・高速モデル（Claude API 既定は Haiku）が「条件を満たしたか」を Yes/No で判定し、短い理由を返す。
  - **No** → 理由を次ターンの指針として Claude が作業を継続。
  - **Yes** → ゴールは自動で clear され、達成として transcript に記録。
- 1セッションにつきアクティブなゴールは1つ。新しい `/goal` は既存を置き換える。
- 条件は**最大 4,000 文字**。
- 必要バージョン: **Claude Code v2.1.139 以降**。
- 実体はセッションスコープの prompt ベース Stop hook のラッパー。`disableAllHooks` や
  `allowManagedHooksOnly` が有効なワークスペース、trust 未承認のワークスペースでは使えない。

## 2. 評価モデルができること / できないこと

| できる | できない |
|---|---|
| 会話（transcript）に出力された内容を読む | ファイルを自分で開く |
| Claude が実行したコマンドの出力を読む | コマンド/ツールを自分で実行する |
| 条件と会話を突き合わせて Yes/No + 理由を出す | 会話に出ていない事実を確認する |

**設計上の帰結**: 条件は「Claude 自身の出力で証明できる終了状態」にする。
「DB を最適化した」のような、会話に証拠が出ない条件は判定不能で空回りする。

## 3. 良い条件の4要素

長く安定して走る条件は概ね次を含む（公式ドキュメント準拠）。

1. **測定可能な唯一の終了状態** — テスト結果 / ビルド終了コード / ファイル数 / 空のキュー など。
2. **証明方法の明示** — どう示すか。例: 「`npm test` が exit 0」「`git status` がクリーン」。
3. **重要な制約** — 途中で変えてはいけないもの。例: 「他のテストファイルは変更しない」。
4. **ターン/時間上限** — `or stop after 20 turns` のような停止句。毎ターンその句に対する進捗が報告され、評価モデルも会話から判断する。

## 4. 良い例 / 悪い例 の対比

| ❌ 悪い（主観的・検証不能） | ✅ 良い（transcript で検証可能） |
|---|---|
| コードを綺麗にして | `npm run lint` が exit 0 になり、その出力を提示。20ターンで停止 |
| 認証機能を直して | `test/auth` の全テストが通り(`npm test -- test/auth` の出力を提示)、`git status` がクリーン。他テストファイル不変。20ターンで停止 |
| パフォーマンスを改善して | ベンチ `npm run bench` の p95 が現状値未満になり、before/after を提示。公開 API 不変。15ターンで停止 |
| ドキュメントを整えて | `CHANGELOG.md` に今週マージした各 PR のエントリが存在(PR 一覧と該当行を提示)。10ターンで停止 |
| リファクタして | 対象ファイルを分割し各ファイル300行未満(行数を提示)、`npm run build` 成功。15ターンで停止 |
| バグを全部潰して | `npm test` が exit 0(出力を提示)、型チェック `tsc --noEmit` がエラー0。25ターンで停止 |

## 5. よくある失敗

- **主観的な条件**（「良い感じにする」）→ Yes/No 判定できない。数えられる状態に置き換える。
- **証明方法を書かない**（「テストが通る」だけ）→ 何をどう提示すれば合格か曖昧。実行コマンドと「出力を提示」を明記する。
- **制約の証拠を残さない**（「他ファイルを変えない」）→ 評価モデルは自力で確認できない。「**毎ターン `git status` を出力し対象外が未変更であること**」のように証拠を会話に出す指示へ翻訳する。
- **上限を付けない** → 条件を満たせないと無限にターンを消費する。必ずターン/時間句を入れる。
- **複数ゴールを詰め込む** → 1つの測定可能な終了状態に絞る。複合なら「A かつ B」を明示し、それぞれの証明方法を書く。

## 6. 運用メモ

- **auto mode 併用**: `/goal` は権限を変えない。既定モードでは未許可コマンド（テスト実行など）で
  都度確認が入り止まる。無人で走らせたいなら auto mode と併用する。`/goal` はターンごとの確認を、
  auto mode はツールごとの確認をなくす補完関係。
- **状態確認**: `/goal`（引数なし）で、条件・経過時間・評価済みターン数・トークン消費・
  評価モデルの最新理由を確認できる。
- **途中終了**: `/goal clear`(別名 `stop` / `off` / `reset` / `none` / `cancel`)。`/clear` でも解除される。
- **再開**: セッション終了時にアクティブだったゴールは `--resume` / `--continue` で復元される
  （ターン数・タイマー・トークン基準はリセット）。達成済み/解除済みは復元されない。
- **非対話実行**: `claude -p "/goal ..."` で1回の起動で完走。長時間走るので
  `--output-format stream-json --verbose` を付けると進捗が見える。Ctrl+C で中断。
- **評価コスト**: 判定は小型モデルで課金され、本体ターンに比べ通常は無視できる程度。
